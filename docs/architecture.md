# Architecture

Joplin Server is a **sync target**: it stores raw items in Joplin's serialized text format and offers no consumer CRUD API for notes. Joplin Web puts an Express backend between the browser and Joplin Server that translates between a small JSON REST API and the sync protocol.

```mermaid
flowchart LR
    subgraph Browser
        A["React SPA<br/>Vite · Tailwind · shadcn/ui · TanStack Query"]
    end
    subgraph Container["Joplin Web container"]
        B["Express backend<br/>auth · note cache · serializer · writer"]
    end
    C["Joplin Server"]
    A -->|"JSON REST /api/*<br/>httpOnly session cookie"| B
    B -->|"Sync protocol<br/>/api/sessions, /api/items/*<br/>X-API-AUTH: &lt;session&gt;"| C
```

In production the backend also serves the compiled client (`client/dist`) on the same port. Content-hashed files under `/assets/` are sent with `Cache-Control: public, max-age=31536000, immutable`; `index.html` (also the SPA fallback) and other files with `no-cache`, so a new release is picked up on the next load.

## Joplin sync protocol

### Endpoints used

| Call | Purpose |
| :--- | :--- |
| `GET /api/ping` | Health check |
| `POST /api/sessions` `{ email, password }` | Login, returns `{ id, user_id }` |
| `POST /logout` (`X-API-AUTH` + `sessionId` cookie) | Ends the session (Joplin Server's web logout; there is no API route for it). Its CSRF check skips `/logout`. Success is a redirect to `<baseUrl>/login`; anything else is treated as failure. |
| `GET /api/items/root:/:/children?cursor=` | Paginated listing of all items (`{ items, has_more, cursor }`), at most 100 per page |
| `GET /api/items/root/delta?cursor=&limit=` | Changes since a cursor (`{ items: [{ item_name, type, updated_time }], cursor, has_more }`, `type` 1 created, 2 updated, 3 deleted; an empty cursor starts at the beginning). `400` with `code: "resyncRequired"` when the cursor was pruned. Used for refreshes after the first listing; a server without it (`404`) is listed in full every time. |
| `GET /api/items/root:/<id>.md:/content` | Raw item text |
| `GET /api/items/root:/.resource/<id>:/content` | Attachment binary |
| `GET /api/items/root:/info.json:/content` | Sync target info (E2EE state), checked before writes (see Write rules); 404 means none yet |
| `PUT /api/items/root:/<name>:/content` | Create or replace an item (multipart, field `file`) |
| `DELETE /api/items/root:/<name>:` | Delete an item |

### Cache refresh

The first refresh notes where the delta feed stands, then lists all items (`/children`, every page) and reads the `.md` items (10 in parallel). Later refreshes read only the changes since from the delta feed (one request when nothing changed), re-read the changed `.md` items and drop deleted ones. When the cursor has expired (`resyncRequired`) or the server has no delta feed, a refresh lists all items again, re-reads only `.md` items whose `updated_time` differs from the cached one and drops items missing from the listing. When it runs:

- **Reads** (lists, tree, tags, search, note, attachment metadata): within `CACHE_TTL_MS` the cache answers directly. Once it has expired, data up to 10 × `CACHE_TTL_MS` old is still served at once while a refresh runs in the background (stale-while-revalidate); concurrent requests share one refresh. The first load, older data, and the first read after a failed refresh wait for the refresh. With `CACHE_TTL_MS=0` every read waits.
- **Writes** (`noteCache.getEntry`) never use expired data: they wait for a refresh (or join the one running), since the E2EE check, link cleanup and tag-name lookups rely on it.
- **Forced** (`POST /api/notebooks/refresh`, notebook purge) always wait; a refresh already running is joined.
- **Errors:** a failed background refresh is logged and handled (never an unhandled rejection) and marks the entry, so the next read refreshes synchronously and its error reaches the error handler like before: an expired session is answered with `401` and marked invalid one request later; an unreachable server answers `503`. The request that started the failed refresh got the stale data.
- Background refreshes use the same "local write" guards as before (see Write rules), so a write made while one runs is not undone.

The delta API (`/api/items/root:/:/delta?cursor=`) is not used yet: it would avoid listing every item, but its change entries carry the change time rather than the item's `updated_time`, a first cursor requires walking the account's whole change history, and an expired cursor needs a full resync.

### Item types (`type_`)

`1` Note · `2` Folder (notebook) · `4` Resource (attachment metadata) · `5` Tag · `6` Note–tag link · `13` Revision. Other types (settings, alarms, …) are ignored. Every item is stored as `<32-hex-id>.md`; attachment binaries live at `.resource/<id>`.

### Serialized format

```text
Title line

Markdown body (notes only)…

id: b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6
parent_id: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
created_time: 2026-10-17T16:00:00.000Z
updated_time: 2026-10-17T16:05:00.000Z
is_todo: 0
type_: 1
```

- Properties are parsed **bottom-up** until the first blank line; line 1 above it is the title, the rest (after one blank line) is the body. Property order is kept on a round trip.
- Only the item times (`created_time`, `updated_time`, `user_*_time`) are ISO strings. `todo_due` (due date / alarm) and `todo_completed` stay Unix ms numbers, `0` when unset, as Joplin desktop writes them.
- Like Joplin's `BaseItem.unserialize`, content is split on `\n` only: a `\r` in the body (CRLF line endings) is part of the text and is written back unchanged. Only property lines are trimmed.
- Newlines in property values are escaped as `\n`, with Joplin's exact escape/unescape chain. That format cannot tell a backslash followed by a real newline from a literal `\n`; Joplin has the same limitation (#55), and matching it keeps values read identically by all clients.
- Notes reference image attachments as `![alt](:/<resourceId>)`, other attachments (including PDFs) as `[name](:/<resourceId>)`, and other notes as `[text](:/<noteId>)`; the client resolves these to `/api/resources/:id` (inline images or PDF viewer, download button otherwise) and in-app links.

### Write rules

- Serialization mirrors Joplin's `BaseItem.serialize`. The title line is always written (even when empty), so a body is never read back as a title.
- Updates start from the item's **original property set** and change only the edited fields plus `updated_time` / `user_updated_time`. Unknown properties round-trip untouched.
- New items get the full default property set Joplin desktop writes (32-hex id, `markup_language: 1`, `source: joplin-web`, …).
- Ids in paths are validated against `^[0-9a-f]{32}$` before any request is made.
- **E2EE:** Joplin Web cannot encrypt. Before writing it checks `info.json`; if `e2ee.value` is true (or the file is unreadable) the write is refused with `422`, so nothing is uploaded in plaintext to an encrypted account. A successful check is reused per session for up to 60 s while the cache listing shows the same `info.json` `updated_time`, so autosaves do not re-read it; a refresh that sees a changed `info.json` forces a new check. E2EE turned on by another client therefore blocks writes after at most the shorter of the cache TTL and 60 s. Without an `info.json` (sync targets older than sync version 3), master key items (`type_: 9`), any `encryption_applied: 1` item, or an item the cache failed to read (it could be a master key) make the account read-only too. Encrypted items (`encryption_applied: 1`) are refused as well, as targets too: no notes or sub-notebooks in an encrypted notebook, no links to an encrypted tag. `GET /api/account/write-state` runs the same check (`noteWriter.getWriteState`) and answers `{ writable: false, reason }` with the exact message a write would be refused with, so the client turns read-only up front instead of failing every save; other failures (expired session, Joplin Server down) are errors as usual.
- **Encrypted items** keep only `id`, `parent_id`, `note_id`, `tag_id`, `updated_time`, `deleted_time` and `type_` in clear (Joplin's `BaseItem.serializeForSync`); title, body and everything else are in `encryption_cipher_text`. The cache never tries to read them: lists, details, the tree, the trash and tags mark them `encrypted: true`; notebooks and tags get the display titles "Encrypted notebook" / "Encrypted tag", notes keep an empty title and body (the client shows "Encrypted note"). Search never inspects cipher text or attachments of encrypted notes, and attachment OCR is only extracted from unencrypted resources.
- Target notebooks (create, move) are re-read from Joplin Server, so one trashed or deleted elsewhere is refused even while the cache still shows it. A note in the trash (or in a trashed notebook) cannot be tagged.
- **Conflicts:** writes carry the `baseUpdatedTime` the editor started from; the writer re-reads the item and answers `409` with the current version if it changed. The UI offers *Overwrite* (`force: true`) or *Load theirs*.
- **Bulk updates:** `POST /api/notes/batch` (up to `MAX_BATCH_SIZE = 1000` items per request) reuses the same E2EE check, active-notebook validation, fresh reads, conflict detection via per-item `baseUpdatedTime`, and `noteCache.upsertItem` updates as single-note writes. Writes toward Joplin Server run with bounded concurrency (`BATCH_CONCURRENCY = 4`, serialized per note id) and return per-item `{ id, status: "ok" | "conflict" | "error", updatedTime?, error?, addedTags? }`, so one conflicting or failing item never aborts the batch (`addedTags` reports only tags newly linked to that note so client undo never removes pre-existing tags).
- **Trash:** deleting sets `deleted_time`. Trashing a notebook also trashes its sub-notebooks and their notes; restoring a note restores its trashed parent notebooks. Restoring a notebook (only one in the trash, else `409`) brings back the sub-notebooks and notes trashed *together* with it, plus any trashed parent notebooks; items trashed on their own earlier stay in the trash. "Together" means a `deleted_time` at most 60 s before the notebook's (`services/trash.ts`): Joplin Web stamps a cascade with one time, but Joplin desktop trashes children first, each with its own `Date.now()`. (Joplin desktop's own restore brings back all notes of a folder and moves items with a trashed parent to the top level instead.) The trash list counts the same way, so its numbers match what Restore brings back. Cascades read every affected item first (up to 10 reads in parallel, level by level) and write only if all pass (no encrypted item), so they never stop halfway on such an item.
- **Conflict copies** (`is_conflict: 1`): when Joplin desktop/mobile hits a sync conflict it keeps a copy of the note with `is_conflict: 1` and `conflict_original_id` in the original notebook, and shows it only in its virtual *Conflicts* folder. Joplin Web mirrors `Note.previews` / `Folder.noteCountsByFolderId`: conflict copies are left out of notebook and tag lists, "All notes", note counts, tag counts and search, and listed only with `GET /api/notes?is_conflict=true` (`is_conflict = 1 AND deleted_time = 0`, wherever their notebook is). Like `Folder.batchDelete`, trashing or purging a notebook leaves its untrashed conflict copies alone (they stay in *Conflicts*, a purged notebook's copies have no notebook any more); a copy in a trashed notebook is therefore not in the trash and can only be purged after trashing it itself. Trashing a copy sets its own `deleted_time` (it keeps `is_conflict`, so restoring brings it back to *Conflicts* without touching its notebook). Editing keeps the flag; moving it to a notebook (its own one too) clears `is_conflict` and `conflict_original_id`, as `Note.moveToFolder` does, which turns it into a regular note.
- **Permanent deletion** only applies to items in the trash, like Joplin's *Delete permanently*. A note is re-read and must be a note (not a notebook, tag or resource), not encrypted, and trashed itself or inside a trashed notebook. Purging a notebook refreshes the cache and re-reads each item, so notes another client moved out are kept. Note–tag links are removed too.
- After each write the cache is updated immediately, so lists reflect the change without waiting for the TTL. Written items get a negative "local write" timestamp, so the next refresh re-reads them and removes them if another client deleted them meanwhile. A refresh that started before a local write or delete does not apply the content it fetched for that item, so a slow refresh cannot put an older version back into the cache (which would cause a false `409` on the next autosave).
- **Joplin Server errors:** a `401`, or a `403` for a session that Joplin Server no longer accepts (re-checked), answers `401` and marks the session invalid, so the client signs in again. A `403` for a valid session stays `403`. `5xx` errors answer with a generic message, never the upstream text.

## REST API (backend → browser)

All routes except `/api/health`, `/api/auth/login`, `/api/auth/logout`, the pending-2FA login/enrollment endpoints under `/api/auth/2fa/*`, and `/api/webhooks/email` (verified via `EMAIL_INGEST_WEBHOOK_SECRET`) require a full verified session (or a validated `mustEnroll` pending login where explicitly noted).

### Search syntax

`GET /api/search` uses a subset of Joplin desktop's syntax, parsed by `services/search-query.ts`. Everything is case-insensitive; trashed notes (and notes in trashed notebooks) are never returned.

| Syntax | Meaning |
| :--- | :--- |
| `shopping list` | Every word must appear in the title, body, or a linked attachment's `ocr_text` (`ocr_status: 2`), in any order (substring match). |
| `"shopping list"` | Exact phrase. An unclosed quote runs to the end of the query; whitespace in OCR text is collapsed per attachment (phrases do not span across separate attachments). |
| `-word`, `-"some phrase"` | The note (title, body and linked attachments' OCR text) must not contain it. |
| `tag:name`, `tag:"two words"`, `tag:none` | The note has a tag with this title (`tag:none` matches untagged notes). Several `tag:` filters must all match; `-tag:` / `-tag:none` excludes. |
| `notebook:name` | The note is in a notebook with this title **or any of its sub-notebooks** (like Joplin desktop). Several `notebook:` filters match any of them; `-notebook:` excludes the notebook and its sub-notebooks. |
| `type:todo`, `type:note` | Only to-dos / only plain notes. |
| `iscompleted:1`, `iscompleted:0` | Completed / open to-dos (implies to-dos). |
| `has:attachment`, `has:ocr` | Notes linking to at least one resource (`:/id`), or linking to a resource with extracted `ocr_text`. Prefix with `-` to negate. |
| `sourceurl:pattern` | Matches the note's `source_url` property (`*` wildcard or substring). Prefix with `-` to exclude. |
| `created:<spec>`, `updated:<spec>` | Date filters on `createdTime` / `updatedTime`: `today`, `week`, `month`, `<N>h`, `<N>d`, `day\|week\|month\|year-<N>`, `YYYY`, `YYYY-MM`, `YYYY-MM-DD`, or `>=`, `<=`, `>`, `<` comparisons. Prefix with `-` to negate. |

Filter values may be quoted; tag and notebook names must match the whole title, with `*` as a wildcard (`tag:proj*`). Unknown filters and invalid values (`foo:bar`, `type:x`) are searched as plain words. A query of only filters is valid and lists all notes that pass them. Linked attachments are resolved from `:/<32-hex>` references in Markdown links/images and HTML `<a href>` / `<img src>` attributes; words may match across the note and its attachments, while negated terms exclude on attachment OCR too. Results are sorted by how many terms match in the title (×100), body (×10), and attachment OCR (×1), then by `updatedTime`. `matches.terms` lists the lower-cased positive words/phrases so the client highlights them; `snippet` is cut around the first term found in the body, or—when all hits came solely from attachment OCR—around the first OCR hit with `matches.matchedIn: "attachment"` (empty for filter-only queries, where the client shows the preview). Note content from OCR is also exposed via `noteCache.getNoteAttachmentText(sessionId, noteId, { maxChars })` in link order.

### Security headers

- helmet's defaults apply to every response, with `img-src 'self' data: blob:` (attachments are shown through `blob:`/`data:` URLs; `https:` is added with `ALLOW_REMOTE_IMAGES`), `media-src 'self' blob:` (inline `<audio>` / `<video>` playback and Voice Note previews), and `Referrer-Policy: no-referrer`. `upgrade-insecure-requests` is only sent when `PUBLIC_URL` is `https://`, so plain-HTTP LAN setups keep working. The Vite dev server sends the same `img-src`.
- `script-src` must stay `'self'` and must **never** allow `'unsafe-inline'`: attachment `blob:` URLs opened directly run in the app's origin, and the CSP is what keeps script in them from running.
- **Serving attachments:** attachments are user content served from our origin, so `GET /api/resources/:id` always sends `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; sandbox` — except `application/pdf`, which omits `sandbox` and adds `frame-ancestors 'self'` (keeping `X-Frame-Options: SAMEORIGIN`) so Chrome and Firefox render PDFs inline in same-origin `<iframe>`s instead of blocking them. Only raster images, PDF, plain text, audio and video are sent `inline`. SVG keeps `image/svg+xml` (so `<img>` can show it) but is sent as `attachment`; every other type (HTML, XML, JavaScript, unknown or malformed types) becomes `application/octet-stream` + `attachment`. File names go into `Content-Disposition` as an ASCII fallback plus RFC 5987 `filename*`.
- The client loads images with `fetch` (session cookie) and renders them from `blob:` URLs. SVG is rendered from a `data:` URL instead (browsers don't open `data:` URLs as documents), and downloads use `application/octet-stream` blobs, so an SVG never becomes a document in the app's origin. Links (`:/id`) whose label ends in `.pdf` (case-insensitive, in Markdown or HTML notes) render through `PdfEmbed` as a card with *Open*, *Download*, and a lazy same-origin `<iframe src="/api/resources/:id">` when `navigator.pdfViewerEnabled !== false`. Note lists carry `thumbnail` (the first `:/id` in the body whose resource is a PDF or a JPEG/PNG/GIF/WebP/AVIF/BMP image). Images are shown with a plain lazy `<img src="/api/resources/:id">`. A PDF's page 1 is rendered client-side by `lib/pdf-thumbnail.ts` once the card nears the viewport (`IntersectionObserver`): `pdfjs-dist` and its Vite-bundled module worker are lazy-loaded, run with `isEvalSupported: false` and `useWasm: false` under `script-src 'self'` (the worker loads pdf.js's no-WASM JBIG2/CCITT and JPEG 2000 decoders by name from `wasmUrl`, so Vite emits them unhashed into `assets/pdfjs-<version>/`; without them scanned pages render blank), at most two PDFs render at a time, and the PNG `blob:` URL is memoized for the session (cleared by `clearResourceCache()` on logout).

### Sessions

- The browser never sees the token: it lives in the httpOnly cookie. On startup the client calls `/api/auth/check`; only the email address (for display) is kept in `localStorage`.
- Rate limits per client address and 15 minutes: `RATE_LIMIT_MAX` requests on `/api/` (default 1000), 30 login attempts on `/api/auth/login`, and 30 mutating (`POST`/`PUT`/`DELETE`) requests on `/api/auth/2fa`. A 429 carries `Retry-After`.
- `TRUST_PROXY` sets Express' `trust proxy`, so `req.ip` (rate limits, logs) and `req.secure` (cookie `Secure` flag) reflect the client behind a reverse proxy. Off by default, so a directly exposed instance can't be fooled by a forged `X-Forwarded-For`.
- Logout (client): unmounts the notes UI so open editors flush their changes, waits for pending writes, calls `/api/auth/logout`, then clears the TanStack Query cache and revokes cached attachment URLs. Login also clears the query cache.

### Two-factor authentication

```mermaid
flowchart TD
    PW["POST /api/auth/login<br/>Email + password verified upstream"] --> Check2FA{"User has 2FA or<br/>REQUIRE_2FA=true?"}
    Check2FA -- No --> Full["Full session<br/>Set session cookie"]
    Check2FA -- Yes --> ClientType{"Origin header?"}
    ClientType -- "Missing (API client)" --> InlineCode{"Valid totpCode /<br/>recoveryCode?"}
    InlineCode -- Yes --> Full
    InlineCode -- No --> EndUp401["End upstream session<br/>401 twoFactor required"]
    ClientType -- "Present (Browser)" --> Trusted{"Valid trusted-device<br/>cookie & enrolled?"}
    Trusted -- Yes --> FullNoStepUp["Full session<br/>No step-up grace"]
    Trusted -- No --> Pending["Pending login in memory + pending cookie<br/>5 min TTL · max 5 attempts · single-use"]
    Pending --> Challenge{"mustEnroll?"}
    Challenge -- Yes --> Enroll["Enroll TOTP or Passkey<br/>Generate 10 recovery codes"]
    Challenge -- No --> Verify["Verify TOTP, Passkey, or Recovery Code"]
    Enroll -- Success --> Full
    Verify -- Success --> Full
    Pending -- "Cancel / Expiry / 5 failures" --> EndUp["Delete pending record<br/>End upstream session"]
```

- **Login state machine:**
  - When password authentication succeeds against Joplin Server, `POST /api/auth/login` acquires `withUserLock` and loads `CACHE_DIR/auth/<ownerKey>.json` (if `CACHE_DIR` is configured).
  - If 2FA is disabled for the user and `REQUIRE_2FA` is `false`, a full session is recorded immediately.
  - If 2FA applies, browser logins (requests with an `Origin` header) with a valid `joplin_web_trusted_device` cookie and already-enrolled factor receive a full session (`twoFactorPassed: true`, `lastSecondFactorAt: null` so sensitive Settings actions still ask for step-up verification).
  - Otherwise, browser logins do **not** receive a session cookie. The upstream Joplin session id stays server-side in memory inside a `PendingLogin` entry (`5 min` TTL, max `5` attempts, single-use `consumed` + `inFlight` lock) keyed by SHA-256 of a random token stored in the httpOnly `joplin_web_2fa_pending` / `__Host-joplin_web_2fa_pending` cookie. Because pending logins are kept in memory, a server restart drops them while their upstream Joplin sessions expire on Joplin Server's schedule. Cancelling (`POST /api/auth/logout`), exceeding 5 failed attempts, or timing out drops the pending record and terminates the upstream Joplin session (`deleteSession`).
  - Pending-mode enrollment (`REQUIRE_2FA=true` while unenrolled) re-derives `mustEnroll` from the live `<ownerKey>.json` record on every `/totp/setup`, `/totp/confirm`, `/passkey/register/options`, and `/passkey/register/verify` call and re-checks `hasPrimaryFactor(record)` inside `withUserLock` right before persisting; if another session enrolled first, late pending enrollments fail with `403`. When `REQUIRE_2FA` is first enabled on an unenrolled account, enrollment is first-enroller-wins, so the account owner should sign in and enroll right away.
  - Once TOTP, WebAuthn passkey assertion, recovery code verification, or mandatory enrollment succeeds, `promotePendingLogin` deletes the pending entry, records the verified session in `TwoFactorStore`, promotes the httpOnly session cookie, clears the pending cookie, and optionally issues a 30-day trusted-device cookie.
  - Non-browser API clients (no `Origin` header, no auth cookies) can pass `totpCode` or `recoveryCode` in `POST /api/auth/login` for single-call authentication; otherwise `401` is returned and the temporary upstream session is closed immediately.
- **Per-user lockout & exponential backoff:** Consecutive failed guessable second-factor checks (pending and step-up TOTP, recovery codes, and the one-call API login) are counted per user in `<ownerKey>.json`; from the 5th failure verification is locked with exponential backoff (1, 2, 4 … up to 60 minutes, `429` + `Retry-After`), across logins and IPs and surviving restarts. Passkeys are never locked and failed passkey assertions are not counted: an assertion can't be guessed, and this keeps the owner a way in while someone who knows the password keeps the codes locked. A successful second factor clears the count, and a failure more than 60 minutes after a lock expired starts a new count. The password step, logout and existing sessions are unaffected.
- **Session binding & step-up:** `CACHE_DIR/auth/sessions.json` maps `sha256(sessionId)` to `{ userId, email, createdAt, twoFactorPassed, lastSecondFactorAt, lastAccessedAt }`. `authenticateSession` refuses requests against `CACHE_DIR` unless a matching verified session exists in `sessions.json`, preventing raw Joplin Server tokens from bypassing Joplin Web's 2FA. (Joplin Server's own sync/admin login is outside Joplin Web and not covered by Joplin Web's 2FA.) When a user enrolls their **first** primary factor (from Settings or pending enrollment), all other recorded sessions for that user are revoked (removed from `sessions.json`, validation cache, and note cache, and ended upstream via Joplin Server) and any existing `trustedDevices` are cleared, keeping only the enrolling/promoted session. Modifying TOTP, passkeys, recovery codes, or trusted devices from Settings requires `lastSecondFactorAt` within 5 minutes (`403 { stepUpRequired: true, methods }`). When `REQUIRE_2FA=true`, removing the last primary factor (TOTP or final passkey) is refused with `400`.
- **Storage layout & security invariants (`CACHE_DIR/auth/`):**
  - Directory mode `0700`; all JSON writes use temp files in the same directory + `chmod 0600` + `rename` (`atomicWriteJson`) serialized through per-user async mutexes (`withUserLock`).
  - `<ownerKey>` is `userId` when matching `^[A-Za-z0-9_-]{1,128}$` and lowercase `sha256(userId)` otherwise. Malformed or unreadable user files fail closed rather than falling back to an empty record.
  - `<ownerKey>.json` (`version: 1`) stores `totp: { secret, createdAt, lastUsedStep } | null` (RFC 6238 SHA-1, 6 digits, 30 s, ±1 step window, monotonically increasing `lastUsedStep`), `passkeys: [{ credentialID, publicKey, counter, transports?, name, createdAt, lastUsedAt }]` (verified via `@simplewebauthn/server` with `userVerification: 'preferred'`, so passkeys act as a possession factor; enforces counter growth whenever `counter > 0 || newCounter > 0`), `recoverySalt` + `recoveryCodes: [{ hash, usedAt }]` (10 × 80-bit codes hashed with per-user salted SHA-256), `trustedDevices: [{ id, tokenHash, label, createdAt, lastUsedAt, expiresAt }]` (capped at 50 active devices, expired entries pruned on write), and `failedAttempts` + `lockedUntil`.
  - Secrets, `otpauth://` URIs, QR URLs, recovery codes, raw tokens, and WebAuthn assertions are never written to logs. TOTP QR codes are rendered with `qrcode` as `data:image/svg+xml;base64,...` images so helmet's strict `script-src 'self'` CSP remains untouched.
  - WebAuthn Relying Party config comes strictly from `PUBLIC_URL` (`rpID = url.hostname`, `expectedOrigin = url.origin`); outside `NODE_ENV=production`, `http://localhost` origins are also allowed when `PUBLIC_URL` is unset.

- `components/auth/SecurityDialog.tsx` + `hooks/use-two-factor.ts`: Security settings dialog reachable from the header avatar menu (`Header.tsx`) to enroll/remove authenticator apps, add/rename/remove passkeys (hidden where unsupported), regenerate recovery codes, revoke individual or all trusted devices, and complete inline 5-minute step-up verification when prompted.

Both skip `["note", id]` queries of notes whose editor has unsaved edits (`setNoteUnsaved`).
- `lib/cross-tab.ts`: `BroadcastChannel` write notifications (`announceWrite`, `onRemoteWrite`, no-op when unsupported) scoped by `draftOwner`. After any write (lists, note saves, attachment uploads), other open tabs of the same user call `invalidateAllExceptUnsaved` immediately without throttling or echoing, leaving unsaved notes untouched.
- `lib/drafts.ts`: unsaved editor text in `localStorage` (`joplin-draft:<noteId>`, with the `baseUpdatedTime` it was based on and its owner, email + Joplin Server host). Written on every edit; removed after a successful save, on logout, on *Sign out and discard*, after 7 days, and on login when the owner differs. The viewer offers to restore a draft that differs from the server text and blocks editing until the user restores or discards it; a restored draft is saved with its original base, so conflict detection still applies.
- `hooks/use-write-state.ts`: `useWriteState()` reads `/api/account/write-state` (refetched with every other query on refresh; counts as writable while unknown, the server still refuses). `NotesPage` passes `readOnly` down: the layout shows a "Read-only" banner with the server's reason, and the sidebar, note list, viewer and trash hide editing, creating, to-do toggles, tags, trash actions and (with the editor) uploads. Any write refused with `422` (mutations via the `MutationCache`, editor saves via `use-note-saver`) invalidates the write state; the editor shows the server's message inline ("Not saved. …") and does not retry a `422`.
- `hooks/use-*.ts`: TanStack Query hooks; `use-mutations.ts` invalidates note/notebook/tag queries after writes and exports `invalidateOtherNotes` to lazily mark cached `["note", otherId]` entries stale (`refetchType: "none"`) so derived fields like incoming `backlinks` reload when navigating to a linked note. `use-note-saver.ts` is the write path for note text shared by the editor and the read-mode checkbox toggle: it sends `baseUpdatedTime`, adopts the returned one, updates the `["note", id]` cache and the lists, marks other cached notes and workspace hubs (`recent-notes`, `tasks`, `hygiene`, `preferences`) stale with `refetchType: "none"`, and exposes the save in flight so callers can run saves one at a time. A title/body save does not refetch any list (autosave would otherwise cost four requests every few seconds against the rate limit): `updateNoteInLists` patches the note's entries in the cached note lists and search results with the returned title, `preview` and `updatedTime`, keeps note lists newest first like the server, and only marks searches stale (matches and snippets may differ; they reload the next time they are shown). The `:/id` link rewrite keeps line breaks so positions still match the note body. Also renders GitHub-style `> [!NOTE]`/`[!TIP]`/`[!IMPORTANT]`/`[!WARNING]`/`[!CAUTION]` callouts (`data-callout`), sanitized `<details>`/`<summary>` toggles, click-to-zoom `ResourceImage` lightboxes, and inline `<audio>`/`<video>` resource players. Formulas render in `MathFormula` with KaTeX *after* sanitizing: the sanitized tree only carries the TeX as text (plus the `math-inline`/`math-display` classes), and KaTeX builds its own markup from it with `trust: false`, so no HTML or links from note content get through. ```` ```mermaid ```` blocks render in `MermaidDiagram` (`securityLevel: "strict"`; script elements, `on*` attributes and `javascript:` links are stripped from the SVG before it is inserted). Both libraries are loaded with dynamic `import()` on first use and stay out of the main chunk; they work under the production CSP (Mermaid's inline `<style>` and KaTeX's inline styles fall under `style-src 'self' 'unsafe-inline'`, KaTeX fonts are served from `'self'` under `font-src 'self' data:`, with `object-src 'none'` and `frame-src 'self' blob:` for inline PDF previews).

Ids must be 32 hex characters; the fragment can't contain quotes, whitespace, `<>` or parentheses.
